## 2. 结构还原：它其实是一个矩阵，不是一个产品

包内 `conf/appId` 暴露了 10 个小程序：

| 代号 | appid | 角色 |
|---|---|---|
| qd_goods | wx7869c97260909c66 | 当前这个：带货选品 + 工具 |
| qd_school | wx4efb9f5359696a20 | 课程 |
| qd_toolbox | wxabfc68fb63f36e2b | 工具箱 |
| qd_data | wx5cf1d69052d02249 | 数据 |
| qd_cometool / qd_usetool | wx8811a9d2fc662331 / wx86fff115b14beaf6 | 工具类 |
| qingdou_watermark | wx65a69fd27fb7e18f | 去水印专站 |
| qingdou_newtool | wx1835d7a8af587fb1 | 新工具 |
| qingdou_findMaterial | wxf8f666136d20630f | 找素材 |

会员购买还跳到一个不在表里的 appId（`wxea1b9bfeca2c2cc1`）。**结论：它把功能、流量、支付拆到多个小程序里，用 `navigateToMiniProgram` 串起来。** 这是应对"单包体积、类目审核、iOS 虚拟支付、单点封禁"的成熟做法。

**拾文不学这个。** 个人/小团队没有这么多主体额度，拆矩阵只会把有限流量摊薄。拾文应做**一个小程序 + 一个 H5 兜底**，功能收敛在 5 页内（见第 4 节）。

## 3. 页面规格（拾文版，5 页）

| 页面 | 首屏元素 | 主交互 | 状态 | 参考（轻抖对应） |
|---|---|---|---|---|
| 导入页 | 大输入框（placeholder 由服务端给平台列表）+ "选文件" + 最近 3 条 | 粘贴→提交；选文件→上传 | 空/有历史/不支持来源 | 首页的"工具 + 输入框"、`brand-search` 组件 |
| 任务页 | 标题、进度条、预计剩余、额度余量、"可离开" | 轮询、取消、失败重试 | queued/running/partial/failed | `videoTextExtract` 轮询页 |
| 阅读页 | 整理稿正文（默认）+ 顶部"精华 / 原图与识别稿" | 复制、导出、追问、加入专题 | 生成中/旧稿/失败 | `videoTextExtractNew` 结果页（只有文案） |
| 资料库 | 列表 + 搜索框 + 过滤 | 搜索、跳原文、删除 | 空/有结果/无结果 | `videoTextLibrary` + 搜索页 + 结果页 |
| 我的 | 额度（小时/份）、到期、用量明细、协议入口 | 充值/兑换、删除数据 | 未登录/试用/会员 | `my` + `memberCenter` |

要点（从它身上学到的，不是抄页面）：

1. **首屏只做一件事**：它首页其实是榜单，工具要往下找；它真正做对的是"输入框永远在第一屏"。拾文导入页同理，别把专题、统计放首屏。
2. **任务页必须有"可离开"的明确文案**，拾文 `ImageEditorial.tsx` 已有类似句子，直接复用措辞逻辑。
3. **结果页一屏到底**：它结果页只有"文案 + 复制 + 再提一条"，没有二级导航。拾文阅读页的三 tab 已经是这个结构，不要加更多层。
4. **资料库的搜索是独立页**：它把搜索做成 `search-page` + `search-result-page` 两页，而不是列表内联。拾文专题检索可以沿用现有一页，但要给"无结果→建议词"。

## 4. 数据契约（字段来自它的 data 初始结构，命名改为拾文）

```ts
// 任务
type IntakeTask = {
  id: string;                 // 任务号
  status: -1 | 0 | 1 | 2;     // 失败 / 处理中 / 完成 / 部分完成
  percent: number;            // 0-100
  eta_sec: number;            // 预计剩余秒（服务端算，前端只显示）
  next_poll_ms: number;       // 下次轮询间隔（服务端下发）
  text?: string;              // 原始转写
  error?: { code: string; message: string };
};

// 额度
type Quota = {
  plan: 'trial' | 'paid';
  hours_left: number;         // 小时余额（不是次数）
  expires_at: number;         // 到期时间戳
};

// 来源预检
type SourceCheck = {
  supported: boolean;
  platform: 'douyin' | 'article' | 'image' | 'unknown';
  fallback?: 'upload' | 'paste_text';   // 不支持时的替代动作
  reason?: string;
};

// 平台白名单（服务端下发，改配置不发版）
type PlatformList = { name: string; hosts: string[]; mode: 'link' | 'upload' }[];
```

**关键经验：额度用"小时"不用"次数"。**
它的 `my` 页字段是 `surplusHours` / `expiredDay`，不是"剩余 N 次"。因为成本随时长线性增长，按小时卖既对得上成本，用户也能自己算。拾文的 45 图整理是文本 token 成本、转写是时长成本，**两种单位要分开**：转写卖小时，整理稿卖"份"。

## 5. 接口契约（拾文命名，路径与轻抖无关）

| 方法 | 路径 | 入参 | 出参 | 说明 |
|---|---|---|---|---|
| GET | `/api/platforms` | — | `PlatformList` | 小程序启动拉一次，缓存 |
| POST | `/api/intake/precheck` | `{ url }` | `SourceCheck` | 提交前判断，避免无效计算 |
| POST | `/api/intake` | `{ url?, file_id? }` | `{ task_id }` | 只收链接或已上传文件 id |
| GET | `/api/intake/{id}` | — | `IntakeTask` | 轮询；`next_poll_ms` 由服务端给 |
| POST | `/api/intake/{id}/cancel` | — | `{}` | — |
| GET | `/api/account/quota` | — | `Quota` | — |
| POST | `/api/account/redeem` | `{ code }` | `Quota` | 兑换码，不做分销 |
| GET | `/api/items?q=&cursor=` | — | 列表 | 资料库检索 |
| DELETE | `/api/items/{id}` | — | `{}` | 删除通道（合规必需） |

工程约束（这几条是它做对、值得照搬的部分）：

1. **提交前预检**：`canUpload` / `source/check` 类接口，先判断再排队，不做无效计算。
2. **轮询间隔服务端下发**：客户端不允许自己定 `setTimeout` 间隔；服务端按队列压力给 `next_poll_ms`。
3. **状态码集中映射**：它的错误码是 4001（额度不足→升级）、21001（内容违规）、9527（停机维护）、70001（处理中重试）、4004（不存在）。拾文用一组枚举统一处理，别在页面里散落 if。
4. **平台列表服务端下发**：加平台/下线平台不发版。
5. **客户端零媒体处理**：小程序不下载、不解码、不跑模型，只传链接与轮询。

## 6. 状态机

```
提交 → precheck
  ├─ supported=false → 引导 upload/paste_text（不排队）
  └─ supported=true  → 建任务(queued)
                        → running（percent/eta 由 worker 写）
                        → done | partial | failed
                        → 取消（用户主动，释放队列位）
```

```
额度：trial(送 X 小时) → 扣减（按实际时长，四舍五入到分钟） → 余额不足 → 引导兑换
      扣减必须与任务终态同一事务，失败要回补
```

## 7. 商业化组件：哪些适合拾文

| 组件 | 它的做法 | 拾文该不该做 | 判断 |
|---|---|---|---|
| 小时余额 | `surplusHours` | 该做 | 与转写成本对齐 |
| 广告解锁 | 每天看一次激励视频当天免费 | 可做，但有门槛 | 微信流量主需累计独立访客达标（具体数值按当期规则核实）；早期没量，别把它设计成主路径 |
| 提交前拦截 | `canUpload` | 该做 | 省钱最有效的一招 |
| 邀请分销 | `invite/checkInviteRelation` + 团队榜 | 不该做 | 拉人头分佣会把产品变成渠道生意，且合规成本高 |
| 跨小程序卖会员 | 跳另一个 appId 收款 | 不该做 | 需要多主体额度；拾文用 H5 兜底即可 |
| 榜单/选品 | 日销量/佣金排序 | 不该做 | 与学习资料定位冲突，且数据依赖抖音生态 |
| 课程 | 学堂小程序 | 不该做 | 不是同一门生意 |
| 云盘 | `cloudDisk` | 暂缓 | 拾文本地库已覆盖，云端存储是成本项 |

**最值得抄的一条商业经验**：它把"敏感功能"（去水印）做成免费 + 免责声明，把收费放在会员时长、课程、带货上。拾文对应的是——**"转文字"作为获客成本，收费落在"整理稿/精华/专题"**。这不是道德判断，是成本结构决定的：转写边际成本低、可替代性高；整理稿是你独有的。

**拾文不要照搬这套色板**（现有 React 工作台已有自己的视觉语言），只借"三级文字 + 一个主色 + 一个成功色"的克制程度。它的界面之所以不花，是因为 90% 的界面只有这三种颜色。

## 9. 可观测性

它的做法：`behaviorLog`（行为）、`errorLog`（错误带 path/functionName/describe）、`channelLog`（渠道）、`sendViewLog`（曝光），外加友盟 + 阿里云 SLS。

拾文的最小版本：

- 一张 `events` 表：`ts / user_id / event / page / payload_json`，只记 6 类事件（提交、预检失败、任务终态、复制、导出、删除）。
- 错误统一走 `/api/errors`，带 `code` 与 `trace_id`，不落用户原文。
- 不做第三方埋点 SDK（省依赖、省隐私争议）。

## 11. 给 ZCode 的审查清单

1. 代码里是否出现 `mediacrawler` / `media_platform` / 其 venv 路径（`extractor.py`、`pipeline.py`、`session.py` 是已知耦合点）。
2. 是否复制了轻抖的接口路径、字段名、文案、图片、appid。
3. 是否存在绕过平台风控的逻辑（伪造 UA/设备指纹、代理池、验证码识别）。
4. 额度扣减是否有事务与对账；失败任务是否回补。
5. `precheck` 是否在排队前执行；无效任务是否计入额度。
6. 内容安全：是否接微信 `msgSecCheck` 或等价检查。
7. 隐私：读取剪贴板是否在协议中明示；是否上传用户原文到第三方（列出域名）。
8. 支付：iOS/Android 是否分端处理；是否在小程序内直接卖虚拟服务。
9. 删除通道：`DELETE /api/items/{id}` 是否删原图/原稿/派生稿/索引四份。
10. 是否把竞品分析文档打进核心包（`build_core_package.py` 白名单应排除）。
