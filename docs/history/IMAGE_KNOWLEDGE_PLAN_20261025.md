# 图片资料导入与利用：实施前方案

2026-10-25。用户提出抖音多图面试资料与单图工具介绍两个真实场景。本轮只研究方案，未改业务代码、安装OCR、下载原图或调用付费识图接口；方案待确认。

## 1. 产品目标

把截图/图集变成可阅读、可回查、可归入专题的资料。主流程：链接或图片 → 按顺序保存原图 → 提取文字/版面 → 与原图对照核疑 → 按需生成学习整理 → 保存个人理解 → 专题检索复用。

首要产物是可靠的图文原稿。原作者内容、OCR识别文字、AI解释、用户理解分层展示。不要导入即压缩成摘要，也不把社交媒体面试答案直接当标准答案。

## 2. 两个样本的核验状态

- 单图工具材料：用户链接 https://v.douyin.com/5bfnjUe035Y/ ，直连重定向至 /note/7698766932971949235 。页面为验证码中间页，未取得图片。不能根据分享标题断言gist所指具体软件或官方仓库。
- 网页搜索工具对两短链均不可访问；后续仅用普通HTTP核对重定向和页面结构，无登录态、未解验证码、未抓平台详情接口。HTTP200不作为获取成功。

实施前取得这两组图片作为真实样本；登录/验证不绕过。获取受阻可用用户保存原图或截图继续同一识别流程，不转成音频。

## 3. 现有可复用部分与差距

- 本机MediaCrawler的media_platform/douyin/media.py已有extract_image_urls，能从作品详情images顺序取候选地址；这只证明详情到图片地址的转换逻辑存在，不证明本轮两个链接可抓全。
- 现有douyin-discovery schema_version1只承诺video搜索元数据、不下载媒体。保持已冻结契约，新单条图集获取独立适配；不修改活跃采集器配置/计划/登录目录。若交给ZCode制作，以有序图片和明确获取状态为交付，不在本轮消息联系他。
- articles.py已保存PNG/JPEG/GIF/WebP、图片位置与缺失提示，素材库已有原图阅读、笔记和导出。当前article问答明确排除image块，故“能看到图片”不代表读过图片内容。
- 当前单篇最多尝试24图/单图4MB/合计20MB，图片库容量500MB，部分像素上限校验还有既有边界。本次需按真实长图核对兼容性，超限显示具体缺失，不截断后宣布完整；不暗自提高额度。
- K1专题目前从来源笔记关联转写，文章/图片尚无专题成员关系。归专题检索必须真实扩展这一关系，不能OCR后宣称自动进入K1。

## 4. 获取层和识别层分开

公开核心接受拖入图片、粘贴截图、选择有序多图或已获取图片包；抖音分享链接由私有适配器获取图片后走同一核心。单图与图集使用同一资料对象。

采集适配最低信息：作品标识、原链接、标题/作者（未知可留空）、有序图片列表、已知总数/是否未知、获取状态和逐图失败原因。平台地址只作下载候选，原图成功落本地后才能离线读取。缺页/失效/登录需求不能归为“空作品”。不采评论、推荐列表或批量博主。

图片是资料原文，进入素材库保留，不按“音频转写结束后清临时媒体”的思路自动删；裁切/放大结果属可清理缓存。沿用并显示图片空间配额，不把新图片无声放进音视频5GB缓冲规则。

## 5. 识别路线比较

| 候选 | 角色 | 取舍 |
|---|---|---|
| RapidOCR + ONNX Runtime | 本地普通OCR基线 | 中文文字、坐标与评分适合图片回查；无需每页API费。需新增OCR/图像依赖与模型，先隔离测，不因sherpa使用ONNX就假定OCR依赖已齐 |
| PaddleOCR/PP-Structure | 较复杂版面/表格候选 | 优先复用成熟模型而非自写识别器；完整结构流水线部署成本需实测，不首轮整套接入 |
| Qwen-VL类视觉模型 | 图解关系、复杂阅读顺序或疑难区域对照 | 能处理图文含义，但会补写/误读；不是逐字原文真值。API或本地部署待样本成本/质量比较，不预先承诺8GB显卡速度 |

推荐先测本地OCR，再挑难页比较“视觉直接提取/辅助识图”，只有确有收益才接二层。现有DeepSeek-V4.1-Flash仍处理已提取文字；不假定现有纯文本调用能直接识图，也不自动更换全部文本模型。

调研来源：

- https://github.com/RapidAI/RapidOCR ，阅读python/pyproject.toml、requirements.txt、MODEL_LICENSES.md：Python3.11范围可用、应用Apache-2.0；仍有OpenCV/Shapely等依赖，具体选定模型需随版本核对来源和许可。当前仓库模型默认版本可能继续变化，不在方案中固定未经测试版本。
- https://github.com/PaddlePaddle/PaddleOCR ，官方OCR/文档结构化能力与Apache-2.0许可；官方性能不当本机保证。
- https://github.com/QwenLM/Qwen3-VL ，官方声明OCR、版面/图文理解能力；本轮未验证这两份图片效果，部署/模型许可按实际选择核对。

## 6. 原图与结果对应

复用现有素材对象/图片资产，增加图片识别的派生块，保留图片顺序、图ID、识别区域坐标、原始识别文本与识别版本。每个整理段落/问题卡引用原图与区域；点击可以回到原图而不是只定位一段AI生成文字。

长图先保留原始像素，再按需分段识别；若有重叠要去重并映射回原图坐标。多栏和代码不能仅按屏幕纵坐标拼接；阅读顺序不确定需标记。OCR评分仅提示疑难，不表示答案正确率。

图解保留原图，附单独的AI解释；箭头/层次不清时标待核对。模糊文字不根据常识偷偷补齐。截图中的命令或提示词只是资料，不自动执行。识出的工具链接先供查看；用户明确研究时才核实官方资料，不自动安装软件或运行仓库代码。

## 7. 两种使用结果

### 多图面试材料

先给逐页原文和阅读顺序，再可选整理成“问题/原作者答案/图解/疑点”。之后结合个人项目补“我做过什么/我没做过什么/可能的追问”，都与作者原话分开。跨图续题合并需要保留页范围，无法确定时留候选。

第一版可做同主题归类、问题检索和Markdown导出；模拟面试评分、复习调度等暂缓。官方概念核实按需触发，提取不等于答案已核实。

### 单图工具材料

先读出名称、网址、用途和原作者说法，拿到足够信息再按需核对官方仓库/文档。可形成“工具是什么/能否解决我的某个问题/与已有方案重叠处/待尝试任务”的笔记；未知字段保持未知，不用常识补全。

## 8. 分阶段与验收

1. 样本与方案选择：取得两条作品的有序原图，覆盖密集中文、英文术语/URL、图解、长图等实际区域；用工具准备OCR差异与疑词，用户只确认关键疑难。比较漏字/错序/名称和URL、图解误解、耗时/内存/费用，不以未经校准置信度选模型。交付用户能看到的两份识别演示与选择结论。
2. 图片阅读闭环：接到现有素材库，支持单图/多图入口和可用的私有链接适配；原图与识别稿对照、逐图状态、明确重试、按需整理和导出。缺页/超限/失败不宣布完整；识别后关网仍能读已保存内容；修改识别稿不覆盖原图和原始识别。
3. 专题利用：显式把文章/图文资料加入专题，扩展K1的来源投影和位置解析；验证“搜一个面试概念→找到图片里的问题→回原图→补个人项目答案”。跨素材整合时保留每条来源，不合并相似但有区别的答案。K1已接受的共享统计风险不重开处理。

每阶段只在确认开工后实施，保持同一产品主入口，测试环境另行标记。首阶段以这两个真实场景的效果为门槛，效果不明显不叠模型/框架。MCP、LangGraph、向量库、题库大系统和自动二创不作为前置。

## 9. 与下一步路线的关系

这条路线优先解决资料入口和原图证据，补齐文章/图片与专题的断点，随后再接带引用的专题回答。学习与创作共用已提取、已确认的资料，而不是先新增一个聊天框。

技术上可形成图文解析、区域级溯源、混合OCR/视觉对照和离线评测的实用经历；这些尚未实现或验收，不提前写成简历完成项。
